02
Synthèse exécutive

L’essentiel du projet

Une codebase qui marche, mais qui fuit, se copie-colle et ne se laisse pas faire évoluer. Nous l’avons rendue durable sans casser son API.

1

L’enjeu

SaaS B2B : une fuite entre entreprises est « le pire incident possible ». L’audit en trouve 3 critiques de plus, des règles d’accès copiées 7 fois et une architecture hexagonale morte.

2

La réponse

Un monolithe modulaire hexagonal (expenses, iam) et une outbox d’e-mails pour notifier les décisions. Contrat d’API inchangé en succès.

3

Le résultat

29 constats sur 46 corrigés et testés, règles d’architecture vérifiées en CI, SonarQube sur le dépôt, et un harnais qui permet d’ajouter une fonctionnalité en un prompt.

À retenirOn n’a pas réécrit : on a rendu les bonnes décisions faciles et les mauvaises impossibles.
Expense.io · SIGL Promo 2027 · 30/10/2026
Message d’ouverture, 45 secondes. Trois phrases : enjeu, réponse, résultat. « 3 critiques de plus » : F1 (reçus lisibles d’une autre entreprise), F2 (RLS contournée), F3 (injection SQL) ; le 4e critique est le secret en dur F25. Le premier incident du cours (fuite A→B) n’est pas théorique ici.

04
Contexte

Expense.io, le point de départ

Étude de cas du cours 2 : un SaaS B2B de notes de frais, entièrement vibecodé.

Le produit
  • Soumission d’une note de frais avec reçu
  • Validation par le manager ou les RH
  • Reçus stockés sur S3, pré-remplissage par OCR
  • Next.js 16, PostgreSQL (RLS), LocalStack S3

Départ : un seul process Node, tout synchrone, SQL brut dans les routes.

Les consignes de soutenance
  • Tout le monde peut créer une note
  • Un manager ne valide que ses subordonnés directs
  • Un RH valide les managers racines, jamais ses propres notes
  • SonarQube doit tourner sur le dépôt
  • L’API ne change pas (ajouts permis)
À retenirDeux contraintes dictent tout : l’API est figée, et la preuve doit être chiffrée.
Expense.io · SIGL Promo 2027 · 30/10/2026
Relier au cours : Manu a ajouté des rôles « à la va-vite » (slide 27-29 du cours 2), copié-collé les contrôles dans chaque route, et un premier incident de fuite est arrivé. Notre codebase est cet état-là, réel. L’API figée est la contrainte qui oriente le choix d’architecture.

Résultats de l’audit

Quatre critiques, huit élevés

46 constats : l’isolation entre entreprises et la sécurité dominent le haut du tableau.

F1 · Critique

Reçus d’une autre entreprise

Un manager obtient une URL S3 signée sur la note de n’importe quelle entreprise.

F2 · Critique

RLS de fait désactivée

L’appli se connecte en superuser : les policies Postgres ne s’appliquent jamais.

F3 · Critique

Injection SQL via sort

Le paramètre est concaténé tel quel dans le ORDER BY.

F25 · Critique

Secret d’auth en dur

Le secret de signature des sessions est écrit dans le code source.

À retenirLe pire n’était pas un bug isolé : c’est qu’aucune barrière ne tenait si une route oubliait son filtre.
Source : docs/audit/AUDIT.md
Citer le lien avec le cours : « une requête mal filtrée » du slide 29. Ici F1 et F2 se combinent : la seule barrière est la clause WHERE de chaque route, et la RLS qui devait être la défense en profondeur est contournée. Les 8 élevés incluent F4 (1er inscrit d’un domaine = RH), F5, F9 (décision concurrente approve+reject), F16 (aucun index), F17/F19 (OCR), F26 (stack dans les 500), F30 (cycle d’organigramme).

Un seul vrai goulot : la connexion

Benchmark k6 sur 15 000 notes, commit 265924b — 169 147 requêtes, aucune erreur.

Débit maximal mesuré, échelle linéaire ; toutes les autres routes répondent en 4 à 15 ms à 1 utilisateur.

4,5 s

médiane d’une connexion à 20 utilisateurs simultanés (bcrypt, coût voulu).

≈ 450 ms

pour l’OCR d’un reçu, dans le process web : saturation rapide (F17).

À retenirLe débit n’est pas le problème : la refacto doit le préserver, pas l’optimiser.
Source : docs/audit/baseline.md · AMD Ryzen 5 4600H · k6 1.3.0
Pourquoi un benchmark « avant » : pour montrer que la refacto ne dégrade pas. Honnêteté : la mesure « après » n’a pas pu être prise sur la machine de référence (une comparaison entre deux machines n’a aucune valeur), le tableau « Après » du dépôt est donc vide. Dire clairement que c’est une limite assumée, pas un oubli.

Inversion des dépendances

Les règles sont vérifiées, pas espérées

Le métier ne dépend pas de la technique (cours 2, slide 47).

dependency-cruiser · CI bloquante
  • domain n’importe que son domaine, shared/actor et shared/errors
  • application : jamais pg, aws-sdk, next, bcryptjs
  • un module n’en voit un autre que par son index.ts
  • worker/ n’importe jamais modules/
  • SQL d’expenses : jamais users ni companies (check:sql)
Une règle, un seul endroit

ApprovalPolicy fait seule foi

Qui valide quoi : manager direct, sinon les RH de l’entreprise, jamais sa propre note.

La RLS ne garde que l’isolation entre entreprises. Plus de règle recopiée 7 fois : celle qui causait F1.

À retenirUne règle écrite une seule fois ne peut pas diverger — et une règle vérifiée en CI ne se contourne pas par oubli.
Source : ADR 0002 · .dependency-cruiser.cjs · scripts/check-sql-boundaries.mjs
Cette slide répond à « Testabilité du coeur métier » et « Inversion des dépendances » du slide 47. Montrer que ce sont des contrôles automatiques : npm run verify enchaîne lint, typecheck, depcruise, check:sql et Vitest. Les consignes (manager = subordonnés directs, RH = managers racines) sont toutes encodées dans ApprovalPolicy.
14
ADR 0003 · asynchrone

Notifier sans dépendre du SMTP

Une décision et son e-mail sont écrits dans la même transaction ; un worker livre ensuite.

Idempotence · cours

Livraison au moins une fois : un doublon est possible, jamais une perte.

DLQ · cours

3 échecs → ligne dead, rejouable par runbook.

Ack · cours

Envoi hors transaction, puis marquage sent ; bail de 2 min.

À retenirUne bonne asynchronie, c’est aussi la plus simple : une table, un worker, aucun broker.
Source : docs/adrs/0003 · docs/runbooks/mail-outbox-rejouer.md
Les cinq options de l’ADR : envoi dans la route (la décision dépend du SMTP), envoi sans await (aucune persistance), outbox d’événements avec worker qui compose (le worker doit charger le métier), outbox + relay + SQS (second saut, DLQ, table d’idempotence pour un seul consommateur), et enfin outbox d’e-mails (retenue). Reprendre les définitions du cours 2 : broker, consumer, ack, DLQ, idempotence. SQS seulement si un autre service doit un jour recevoir l’événement.

ADR 0004 · contrat d’API

Le contrat ne change pas : il s’enrichit

Erreurs en RFC 9457, de façon additive.

Avant 
500 { "error": "…",
      "stack": "C:\…\route.ts:42" }
403 / 401 incohérents
id invalide, corps illisible → 500

Stack exposée (F26), codes d’autorisation inconsistants (F27), entrée malformée en 500 (F42).

Après 
application/problem+json
{ "error": "…",            // conservé
  "type", "title",
  "status", "detail" }       // ajoutés

401 = pas de session, 403 = mauvais rôle, 400 = entrée invalide. Jamais de stack.

Garde-fous : docs/api/openapi.yaml est la référence, oasdiff breaking compare à main en CI, CHANGELOG.md consigne chaque écart.

À retenirContract first : on corrige les erreurs sans casser un seul client existant.
Sources : docs/adrs/0004 · CHANGELOG.md · docs/api/openapi.yaml
Remplacer { error } par un RFC 9457 aurait cassé les clients qui lisent « error » : on l’ajoute en plus (option 3 de l’ADR), version MINOR. Retrait possible dans une version majeure. Lien cours : « Contract First » du slide 40 (valable pour les messages comme pour les API). Une route ne construit jamais une réponse d’erreur : elle lève, route() traduit.

Limites assumées

Ce qu’on n’a pas fait, volontairement

KISS : toute absence est un choix écrit, pas un oubli.

OCR toujours synchrone

Un endpoint 202 + polling changerait le contrat. Atténué : moteur réutilisé, 10 Mio max, concurrence plafonnée, 503 Retry-After.

Pagination & limitation de débit

Pagination = nouvelle forme de réponse (contrat). Rate limiting = sujet d’infrastructure (reverse proxy), pas de code applicatif.

RH seul dans son entreprise

Il peut soumettre une note mais n’a aucun validateur tant qu’un second RH n’existe pas — conséquence de la consigne « tout le monde peut créer une note ».

Mesure « après » du benchmark

Non prise : la machine de développement n’est pas celle de la mesure de référence. Une comparaison entre deux machines n’aurait aucune valeur.

À retenirSavoir dire non, et l’écrire, fait partie de l’architecture.
Sources : spec architecture cible · ADR 0002 · baseline.md
Préparer les questions du jury sur ces quatre points : ils ont tous une raison liée au contrat figé ou à la méthode. Autres limites connues : F6 (un domaine = une entreprise, usurpation possible), livraison d’e-mail « au moins une fois » (doublon possible), données personnelles dans mail_outbox (purge à 30 jours).
