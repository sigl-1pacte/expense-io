Le périmètre · tranché

Ce que la refacto corrige, et ce qu'elle laisse au produit

corrigé quelle que soit l'option

Règles de validation

corrigées, et portées par l'architecture

Deux notions à ne pas confondre

Monolithe modulaire et hexagonal répondent à deux questions différentes

Entre les domaines

Monolithe modulaire

Comment découpe-t-on l'application ?

Par domaine métier : expenses pour les notes de frais, iam pour les utilisateurs et les droits. Un module ne touche à un autre que par son API publique (index.ts). On garde un seul déployable, une seule base, et des appels en mémoire.

Dans un composant

Hexagonal (ports & adapters)

Qui dépend de qui ?

Le métier, au centre, ne connaît aucune technologie. Il déclare ses besoins sous forme de ports (NoteRepository, ReceiptStorage). Des adapters les implémentent avec Postgres, S3 ou Tesseract. Une route HTTP est un adapter d'entrée.

Une même règle, « ce manager peut-il valider cette note ? », écrite de quatre façons

Modules, SQL direct

La règle existe une seule fois, dans iam.canDecide(), mais elle est écrite en SQL : on ne la teste qu'avec une base.

Modulaire · hexagonal

Option B

Chaque module est son propre hexagone. canDecide() est une fonction pure du domaine iam, testable sans base, appelée par expenses via l'API publique de iam.

Le modulaire, c'est le plan de l'immeuble et les portes de chaque appartement. L'hexagonal, c'est l'aménagement intérieur, avec des prises standard où l'on branche n'importe quel appareil.

Option A ÉCARTÉE

Monolithe en couches, nettoyé

On garde la forme actuelle et on la range : routes, puis services, puis repositories SQL. La couche hexagonale morte est supprimée.

Ce qu'elle règle

  • La duplication : une fonction decide() remplace les 4 handlers, un seul mapper remplace les 7 copies.
  • Les contrôles d'accès, centralisés dans guard.ts.

Ce qu'elle ne règle pas

  • Le métier reste dans le SQL : aucune règle n'est testable sans base.
  • Les domaines restent mêlés : le service des notes connaît la hiérarchie.
  • Rien côté asynchrone.

Pourquoi on l'écarte. Son seul vrai argument était le coût (3 à 4 jours-personne). Avec des agents, il ne pèse plus. Et A guide mal un agent : on sait où mettre une route, pas où mettre une règle métier.

Option B CANDIDATE

Monolithe modulaire, hexagonal dans chaque module

Un seul déployable, découpé en deux modules métier. Chaque module suit l'hexagonale : domaine pur, use cases, ports et adapters. Les routes Next.js deviennent des adapters minces.

Flèche pleine : appel. Flèche pointillée : l'adapter implémente un port du module (les ports de iam ne sont pas dessinés).

Arborescence

src/
  app/api/**/route.ts   # parse → use case → HTTP
  modules/
    expenses/
      domain/           ExpenseNote.ts
      application/      decide-expense-note.ts …
      ports/            NoteRepository.ts …
      infrastructure/   PgNoteRepository.ts …
      index.ts          # API publique
    iam/                # même structure
  shared/               errors · unit-of-work

Règles vérifiées en CI

  • domain n'importe rien.
  • application n'importe que domain et ports.
  • infrastructure implémente les ports.
  • Un module n'en importe un autre que par son index.ts.
  • app/ n'importe que des index.ts.

Contrôlé par dependency-cruiser. Le nombre de violations est aussi une mesure avant / après.

Ce que B règle dans le périmètre

  • L'agrégat porte la transition pending → décidée, appliquée par un UPDATE … WHERE status = 'pending' F9
  • Une seule ApprovalPolicy F5 F14 F30 F33
  • La soumission passe par une unité de travail F10
  • iam relit le rôle en base F31
  • Fin de la duplication et de la couche morte

Limite. Rien d'asynchrone. L'axe « Asynchrone & run » se réduit à une décision documentée de ne pas en faire.

Point de design. La file du manager fait expense_notes ⨝ users, une jointure entre deux modules. Il faudra choisir comment la traiter (voir D4).

Option C PROPOSÉE PAR L'ÉTUDE

B, plus un flux asynchrone : outbox, file et worker

On part de B. Un second process, le worker, prend en charge les effets de bord qui ne doivent pas bloquer la réponse HTTP. Premier flux : la notification de décision, prévue (NotificationPort) mais jamais appelée F15.

  1. Le manager approuve une note.
  2. Le use case met à jour la note et écrit l'événement dans l'outbox, dans la même transaction.
  3. Le relay du worker lit les événements de l'outbox.
  4. Il publie expense.note-decided.v1 sur la file.
  5. Le consumer reçoit le message.
  6. Il envoie l'e-mail, puis supprime le message (ack).

Garde-fous (cours 2, slide 40)

  • Outbox : la note et l'événement sont écrits ensemble, ou pas du tout.
  • Idempotence : une table processed_messages ; un message rejoué n'envoie pas de second e-mail.
  • Contrat versionné, décrit en AsyncAPI ou JSON Schema.
  • Traçabilité : un correlationId suit la requête, l'outbox puis le worker.
  • DLQ après 3 échecs.

Quels flux justifient l'asynchrone ?

NotificationEffet de bord non critique, aucune réponse d'API ne change. Un SMTP lent ne doit pas faire échouer une décision. F15
OCRSort Tesseract du process web, noté Élevé dans l'audit. Coût : un nouvel endpoint 202 suivi par polling (changement MINOR) et l'UI à adapter. F17 F19 F21

Broker

SQS + outboxProposé. Aucune nouvelle infra (LocalStack est déjà là), chaque notion du cours est visible, et c'est une vraie cible AWS.
pg-bossPlus simple : file dans Postgres, envoi dans la même transaction. Mais le broker se confond avec la base, la démonstration est moins lisible.

Option D ÉCARTÉE

Microservices

Un BFF Next.js garde les routes /api/* publiques, devant un service des notes et un service des permissions, chacun avec sa base, plus un bus et un worker.

Réexaminée sans contrainte d'effort, elle reste écartée

  • Bases séparées. La jointure expense_notes ⨝ users disparaît, alors que les files d'attente et la RLS en dépendent. Les correctifs d'isolation F1 F2 F44 s'appuient sur cette base unique.
  • Transactions distribuées. Soumission et décision deviennent des sagas, précisément là où F9 et F10 demandent de l'atomicité.
  • E2E fragiles. 5 conteneurs ou plus et un tracing distribué, alors que 100 % des E2E doivent rester verts.
  • Live coding plus lourd. Une feature transverse touche deux services et un contrat interne.
  • Rien ne la justifie. Ni la charge, ni des équipes autonomes, ni des déploiements indépendants. Le mémo du cours la range dans « À reconsidérer » (slide 17).

Un agent écrit ce code vite, mais il ne retire pas ces coûts. Il les déplace vers le run et le débogage.

Dans l'ADR, D sert d'alternative écartée explicitement. C'est là qu'elle montre la posture d'architecte.

À décider ensemble

Une proposition, et ce qu'il reste à trancher

Proposition : C, soit B plus un asynchrone limité et justifié flux par flux

  • C'est la seule option qui donne un livrable concret à chacun des trois axes.
  • Chaque choix s'appuie à la fois sur une slide du cours et sur un défaut mesuré dans l'audit.
  • Elle reste réversible : le worker et ses deux tables se retirent sans toucher l'API.
D1

B + C, ou B seul ?

Le critère qui fait basculer est le barème de l'axe « Asynchrone & run ». S'il est noté, B seul ne laisse à son owner qu'une décision documentée. S'il est facultatif, B seul se défend bien.

D2

Quels flux asynchrones ?

La notification seule, ou la notification et l'OCR en 202 avec polling. Mesurer le coût actuel de l'OCR (latence, CPU, impact sur les autres routes) donnerait un chiffre pour trancher.

D3

Quel broker ?

SQS avec outbox (proposé), ou pg-boss.

D4

Jointures entre modules ?

Frontière stricte : iam fournit les utilisateurs rattachés, expenses filtre ses notes (deux requêtes). Ou une vue en lecture seule partagée, documentée comme exception.

D5

Hexagonal ou Clean ?

Pour le cours, les deux se valent. Proposé : le vocabulaire hexagonal, déjà celui du dépôt, avec un fichier par use case.
