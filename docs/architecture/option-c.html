Expense.io · refacto · option C PROPOSÉE PAR L'ÉTUDE

Monolithe modulaire, hexagonal et asynchrone

Un seul code et une seule base, découpés en deux modules métier. Chaque module protège son métier derrière des ports. Un worker traite à part les effets de bord qui ne doivent pas ralentir la réponse HTTP. Et l'API ne change pas.

Pourquoi C

  • C'est la seule option qui donne un livrable concret aux trois axes : Architecture, Contrat d'API, Asynchrone & run.
  • L'asynchrone y est justifié flux par flux, pas posé par principe.
  • Elle reste réversible : le worker et ses deux tables se retirent sans toucher l'API, et on retombe sur B.

Asynchrone

Outbox, file SQS et worker, pour des flux choisis. Premier flux : la notification de décision.

= option B
= option C
  1. Le manager approuve : POST …/approve. La réponse 200 est la même qu'aujourd'hui.
  2. Le use case decide vérifie le droit avec ApprovalPolicy, met à jour la note et écrit l'événement dans l'outbox, dans la même transaction.
  3. Le relay du worker interroge l'outbox à intervalle régulier (polling) et récupère les événements pas encore publiés.
  4. Il publie expense.note-decided.v1 sur la file.
  5. Le consumer, adapter d'entrée du worker, reçoit le message.
  6. Il appelle le use case sendDecisionEmail, qui envoie l'e-mail par le port Mailer.

Comment lire le schéma. Les ronds sur le bord de l'hexagone sont les ports. Tout ce qui est dehors est un adapter, remplaçable sans toucher au métier.

Le worker est une deuxième porte d'entrée vers le même cœur. Le domaine ne sait pas qu'il y a de l'asynchrone.

Worker = même code, process séparé. Ce n'est pas un autre service : il part du même dépôt, des mêmes modules et de la même base, lancé par src/worker/main.ts à côté de next start. On le sépare pour isoler les pannes (un SMTP lent ne touche pas le site) et parce que Next.js n'est pas fait pour des boucles de fond.

Flèche 3. Elle suit les données, qui vont de la base vers le relay. C'est pourtant le relay qui va les lire : la requête HTTP n'écrit que dans Postgres.

L'API ne change pas

Les fichiers api/**/route.ts restent à leur place. Ils lisent la requête, appellent un use case et renvoient la même réponse qu'avant.

Preuves : la suite ARLA-9 reste verte, et le contrat OpenAPI de l'API actuelle est vérifié par oasdiff en CI.

Ce qui bouge volontairement : les réponses d'erreur corrigées (500 → 400, 401 → 403, 409 pour une seconde décision), et la file RH, plus complète mais au même format. Un OCR asynchrone serait un endpoint ajouté, donc une version MINOR.

Ce que C corrige

  • Deux décisions simultanées : l'agrégat n'accepte qu'une transition depuis pending, appliquée par un UPDATE … WHERE status = 'pending' F9
  • Qui valide quoi : une seule ApprovalPolicy. Plus de note sans validateur, plus de cycle, un manager de la même entreprise F5 F14 F30 F33
  • Soumission et inscription dans une unité de travail F10 F11
  • Rôle relu en base par iam F31
  • Notification de décision enfin envoyée F15
  • Fin de la duplication et de la couche morte F22 F23 F24

S'y ajoute le socle commun, indépendant de l'option : isolation, contrôles d'accès, entrées et secrets F1–F3 F25–F27 F42–F44.

Garde-fous de l'asynchrone

  • Outbox : la note et l'événement sont écrits ensemble, ou pas du tout.
  • Idempotence : une table processed_messages. Un message rejoué n'envoie pas de second e-mail.
  • Contrat versionné : expense.note-decided.v1, décrit en AsyncAPI ou JSON Schema.
  • Traçabilité : un correlationId suit la requête, l'outbox puis le worker, avec des logs JSON.
  • DLQ : après 3 échecs, le message part en file d'erreur au lieu de boucler.

Ce que ça ajoute à l'exploitation : un second process (le worker), une file SQS sur LocalStack (déjà présent) et Mailpit en local, à ajouter au docker-compose et à la CI.
